# Assay

ポケモンユナイト（5v5）の非公式ランクマッチシステムです。本家レジェンドランク以上のプレイヤーが決まった時間に集まってソロでキューに入り、独自のレートで対戦します。いわば「ユナイト版スマメイト」です。

> **運用は終了しています。** ポケモンユナイトのサービス終了（2027年3月23日）が決まったため運用を終え、本番環境も撤去しました。このリポジトリは完結したプロジェクトの記録として公開しています。

## 実績

- **開発期間 12日**（設計・実装・本番構築まで）
- **2026年9月12日に開幕し、初日の参加者は340人**。開幕初日は不具合なしで回りきりました
- Discord サーバーの参加者は約900人、**ピーク時の同時接続は約490人**
- プロプレイヤーの配信でも使われました
- **サーバー費は月20ドル程度**。2vCPU / 6GB RAM の VPS 1台で、アプリ・DB・リバースプロキシをすべて動かしていました

## 何をするシステムか

1. Discord OAuth でログインして登録する
2. 希望ロールを最大3つ、優先度付きで選んでキューに入る
3. マッチメイカが3分ごとにキューを走査し、レート差とロール構成が成立する10人を組む
4. Discord の招集チャンネルとチームごとのVCに通知が出る。ホストの打診、ルームIDの共有、勝敗の報告はすべてサイトのマッチ画面で行う
5. 10人がブラインドで勝敗を報告し、一致すれば確定してレートに反映される。割れた試合は運営の Discord チャンネルに回る

運営向けに、マッチメイカの停止・再開、キューからの強制離脱、レート補正、シーズン管理、係争の裁定、シャドウバンなどを行える管理パネルがあります。

## 設計の要点

詳細は [`docs/`](docs/) にあります。特に [`02-設計判断ログ`](docs/02-設計判断ログ.md) には、却下した案とその理由も残しています。

### 試合ログが唯一の正、レートは導出値

試合ログは追記専用で、UPDATE も DELETE もしません。取り消しは打ち消しのレコードを追記して表します。現在のレートはどのテーブルにも保存せず、毎回ログから導出します。

```
現在レート = 1500 + Σ 運営による補正 + Σ 確定した試合の増減
```

再計算の経路はこの1本だけです。そのため、レートのアルゴリズムやパラメータを開幕時点で決め切る必要がありませんでした。ログさえ正しく貯めておけば、あとで式を変えて過去分ごと引き直せます。実際、開幕の前後で、増減の幅や判定に使うレートの扱いを何度か変えています。

壊れたデータが入っても、システムは止まらずに劣化したまま動き続けるようにしています。状態の導出は失敗させず、`(状態, 異常のリスト)` を返します。追記専用で不正なイベントを消せない以上、導出が失敗すると、その試合は二度と読めなくなるからです。

### 報告はAPIレベルでブラインド

他人の報告内容が、まだ報告していないプレイヤーに届く経路を作っていません。確定条件は「報告した人の中での全員一致」で、多数決は採りません。5対4のような非対称な報告数は正常に起きるためです。報告の訂正は追記で受け付け、確定には各自の最新の報告を使い、報告一致率の指標には最初の報告を使います。訂正で多数派に合わせれば指標をすり抜けられる、という抜け道を塞ぐためです。

### マッチメイキング

総当たりはしていません。キュー40人から10人を選ぶ組み合わせは約8億通りあるからです。代わりに、次の手順で組みます。

1. レート順に並べ、幅50のウィンドウで候補を取る
2. ウィンドウ内の候補に対して、ロール枠への割り当てを**最小費用流**で解く
3. 成立した10人のチーム分けは総当たり（126通り）で、平均レートの差が最小になる分け方を選ぶ

選抜は DB にも Discord にも触らない純粋関数として書き、ランダムに生成した2000通りのキューで不変条件をテストしています。開発時の実測では、キュー100人で288µs、200人で5.3msでした。

### DB 権限はホワイトリスト

アプリ用のロールの既定権限は SELECT と INSERT だけです。UPDATE と DELETE は可変テーブルにだけ個別に付与し、付与した理由をコメントで残しています。新しいテーブルは自動的に追記専用になります。テストも所有者ではなくアプリ用のロールで走らせているので、権限まわりのバグが本番でしか出ないということが起きません。行ロックの代わりに `pg_advisory_xact_lock` で直列化しているのも同じ理由です（`SELECT ... FOR UPDATE` は UPDATE 権限を要求します）。

### 復帰の入口は1つ

HTTP のハンドラから Discord は呼ばず、Discord への投稿はすべて、DB の状態を5秒ごとに走査するループから出しています。プロセスが落ちても、再起動すれば続きから進みます。

## 技術スタック

- **Rust** / axum / sqlx（ORM なし、コンパイル時クエリ検証）/ serenity
- **PostgreSQL 17**
- 本番は VPS 上で Caddy（TLS 終端）と systemd で動かし、Cloudflare R2 にバックアップを取っていました。バックアップは隔離環境への実復元まで確認しています
- GitHub Actions でテストとリリースビルドを回し、本番にはビルド済みのバイナリを配置していました

構成は Rust の1プロセスと PostgreSQL だけです。セッションは署名付き Cookie で持ってセッションストアを立てず、キャッシュ層やメッセージキューも置いていません。状態はすべて PostgreSQL に寄せています。ピーク時に約490人が同時に接続しても小さな VPS 1台で足りたのは、この構成のおかげです。

規模の目安：本体は Rust で約4万行、テストは406件、マイグレーションは44本です。

## 開発の進め方

実装はAIコーディングエージェントに任せました。要件定義、設計判断、DBスキーマと権限設計、本番の構築と運用は自分で行っています。

エージェントが判断を取りこぼさないように、設計判断はすべて `docs/` に書き、エージェントにはそれを読ませる運用にしました。複数のエージェントを並行させるときは `git worktree` で作業ツリーを分け、マージとコンフリクトの解消は人間がやる、というルールで回していました。

## リポジトリの構成

```
src/
  matchmaker/    10人の選抜（ウィンドウ＋最小費用流）
  rating/        レートの導出
  lifecycle/     試合の状態機械
  queue/         キュー
  match_screen/  マッチ画面（ホスト打診・ルームID・報告）
  discord/       Discord への通知、VC プール
  registration/  Discord OAuth と登録
  admin/         運営パネル
migrations/      追記のみ（既存のマイグレーションは書き換えない）
ops/             デプロイ・バックアップ・復元の手順と設定
docs/            仕様と設計判断（日本語）
```

`docs/` は開発中に書いた作業用のドキュメントです。「現在地」などの記述は、書いた時点の状態のままになっています。

## ローカルで動かす

DB なしで単体テストを回すだけなら、次のコマンドで動きます。

```sh
SQLX_OFFLINE=true cargo test --lib
```

DB を使うテストには PostgreSQL 17 が必要です。ロールの構成は `ops/ci_roles.sql`、CI の手順は `.github/workflows/check.yml` を参照してください。
