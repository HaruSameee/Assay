CI は `postgres:17` を使用し、通常接続はアプリ用。隔離 DB の生成・マイグレーション・fixture 適用だけ管理用接続を使い、テストのリポジトリ操作はアプリ用に切り替える。権限 SQL は本番と共通であり、CI 用の複製は置かない。

**2026-09-05 初回構築の検証記録**: VPS `203.0.113.1` の PostgreSQL 17.11、DB `assay` に2件のマイグレーションを `assay_migrator` 接続で適用済み。全テーブルの所有者は同ロール。両ロールとも superuser / CREATEDB / CREATEROLE / REPLICATION / BYPASSRLS なし。権限 SQL の2回実行、アプリの42501、所有者の0A000、INSERT / SELECT、可変テーブルの UPDATE、監査0行を確認した。検証変更は ROLLBACK し、formations / players は0行。待受は `127.0.0.1:5432`、資格情報は root 所有・0600。既存マイグレーションはここから不変とし、変更は新規ファイルで追加する。

## 2. デプロイ

VPSは2コアなので、Rustのビルドは遅い。**GitHub Actions で `--release` ビルドしてバイナリを配る**のが速い。副産物としてVPSにRustツールチェーンが不要になり、本番の表面積が減る。

手順:

1. CI で `cargo build --release`（`SQLX_OFFLINE=true`）してアーティファクトを出力
2. バイナリをVPSに転送
3. `assay_migrator` でマイグレーションを適用（必要なとき）
4. **マイグレーションを適用したら、その直後に必ず同じ接続で `ops/app_role.sql` を実行する。**「新しいテーブルを足したときだけ」ではなく毎回流す
5. アプリ接続で `ops/check_app_role.sql` が0行であることを確認
6. systemd で再起動

**4を必ず毎回実行する理由**: `ops/app_privileges.sql` の `alter default privileges` は、**それを実行したロールが以後に作るテーブル**にしか効かない。本番のテーブル所有者は `assay_migrator` だが、CI では `#[sqlx::test]` が隔離DBを作る都合で所有者がスーパーユーザーになるため、`for role assay_migrator` としての効き目はCIでは検証されない。既存テーブルへの `grant select, insert on all tables` は毎回の実行で明示的に付け直されるので、**毎回流す運用にしておけばこの乖離は無害になる**。逆に「必要なときだけ」にすると、CIが緑でも本番の新テーブルだけ権限が付かない、という形で表面化する。

**本番にデプロイした後は、マイグレーションを書き直さないこと。**以後の変更は必ず新しいマイグレーションで積む。

## 5. 開催当日の手順

### 開始前

1. アプリとDBが動いていることを確認
2. VCプールの名前解決が通っていることを起動ログで確認
3. `ROOM_MAP` が今のランクマのマップと一致していることを確認
4. バックアップのcronが動いていることを確認

### 開催中に見るもの

- **キューの待ち時間** — 長ければマッチング範囲が狭すぎる。デフォルト値の校正材料
- **`abandoned` の発生数と理由** — `vc_pool_exhausted` が出たらプールを増やす
- **`disputed` の件数** — スタッフ裁定が必要
- **報告ゲートに引っかかっている人数**

### 落ちたとき

冗長化していないので、**復旧は手作業**。4時間の窓で落ちると次の開催まで1週間空くため、原因究明より復旧を優先する。

1. systemd が再起動を試みているか確認
2. 起動時に未終了 formation を読み直して復帰する設計になっている（Phase 4 / 5）
3. 進行中だった試合は、参加者に「そのまま続けて、終わったら報告して」と伝える。試合そのものはDiscordとゲーム側で進むので、アプリが落ちても試合は成立する
4. 復帰後、`Anomaly` と `discord_failures` を確認する

### 終了後

- [ ] フルダンプを取る
- [ ] レーティングをオフラインで回す（初週は暫定パラメータでよい）
- [ ] 待ち時間・`abandoned`・`disputed` の数字を見て、翌週の設定を決める
