# 04-試合ライフサイクル仕様

**作成**: 2026-09-04
**スコープ**: マッチ成立 → ロビー生成 → 試合 → 報告確定 までの状態機械
**位置づけ**: 03-技術仕様 の一部。9/12の初回開催で動いていなければならない範囲

---

## 0. なぜこの文書が要るか

00の7章（実装順序）は「マッチメイキング → レーティング」と書いてあるが、その間に**マッチが成立してから試合が始まるまでの手順**が抜けている。ユナイトに外部APIが無い以上、部屋は人間が立てる。その人間を指名し、部屋コードを回収し、9人に配り、失敗したら畳む、という手順は自動化しないと回らない。

規模の見積もり: 同接40人で4ロビー、96人フル参加で9ロビー。1日16ラウンドとして、週末1回で **200〜300回** この手順が走る。

---

## 1. 状態機械

```
  matched ──► awaiting_host ──► awaiting_code ──► in_progress ──► awaiting_reports ──► confirmed
                   │                  │                                   │                 
                   │                  │                                   ├──► disputed
                   ▼                  ▼                                   │
               abandoned          abandoned                               └──► voided
```

| 状態 | 意味 | 次へ進む条件 | タイムアウト |
|---|---|---|---|
| `matched` | マッチメイカが10人を確定。formation凍結済み | VC の組を割当・通知完了 | なし |
| `awaiting_host` | ホストを指名し、承諾を待つ | ホストが「作る」を押す | **90秒** → 次の候補へ |
| `awaiting_code` | ホストが部屋を作り、コードを貼るのを待つ | コードが投稿される | **180秒** → 次の候補へ |
| `in_progress` | コードを9人に開示済み | 最初の報告が届く | **45分** → `voided` |
| `awaiting_reports` | 報告受付中 | 確定ルール（03参照）を満たす | 最初の報告から**30分**。確定・係争の評価は Phase 6 |
| `confirmed` | 勝敗確定。レート計算の入力になる | — | — |
| `disputed` | 報告が拮抗。スタッフ介入待ち | — | — |
| `voided` | 試合が成立しなかった。レートに影響させない | — | — |
| `abandoned` | ホスト候補が全滅、または人が集まらず解散 | — | — |

**ホスト候補が尽きたら `abandoned`。** 10人全員を試すのではなく、上位3人まで試して駄目なら解散する。それ以上粘っても10人を拘束するだけで、次のラウンドに回したほうが早い。

## 2. ホストの選び方（要再検討）

### 現在の決定

レートが一番上の人をホストに指名する。

### この決定の問題

**負担がレートに対して単調増加する。** ランキング1位の人は、自分が参加するほぼ全てのロビーで最上位になる。つまり毎試合ホストをやることになる。上位者はこのシステムの看板であり、配信者候補であり、LFT指標として一番見られる人たちで、一番機嫌よく回ってほしい層。そこに構造的な作業税をかける設計になっている。

**レートはホスト適性の代理変数として情報を持っていない。** 実際に効くのは「いま端末の前にいるか」「回線が安定しているか」「部屋設定を間違えないか」で、レートはそのどれとも相関しない。

**部屋設定の権限がホストに乗る。** ドラフトの有無、もちものレベル、使用スタジアム、ライセンス解放状態。これが全ロビーで揃っていないと、ログ同士が比較可能でなくなる。00の3章「試合ログが唯一の正」に直撃する。設定権限を「一番強い人」に渡す理由は無い。

### 代案

**直近ホスト時刻が最も古い人（LRU）。** DBに `last_hosted_at` を1カラム足すだけ。上位への課税がゼロになり、負担が全員に均等に散る。同点はレート降順で割る。

### 決着のさせ方

`HostSelector` trait にして差し替え可能にする。既に「レーティングとマッチメイキングは trait 越しに差し替え可能」という方針があるので、そこに乗せる。デフォルトを `HighestRating` にして初週を回し、上位から苦情が出たら `LeastRecentlyHosted` に切り替える。切り替えコストが1行なら、今ここで結論を出さなくてよい。

```rust
trait HostSelector {
    /// 優先順に並べたホスト候補を返す。先頭から順に打診する
    fn candidates(&self, formation: &Formation) -> Vec<PlayerId>;
}
```

## 3. Discord側の設計

### VC テキストチャット

**試合ごとのプライベートスレッドは作らない。** 事前作成した `vc<N>-red` / `vc<N>-blue` の VC に付属するテキストチャットへ投稿する。専用サーバーはブースト0であり、プライベートスレッドのブースト要件に依存しないためである。

- 割り当て表、集合先、部屋設定、部屋コードは red / blue 両方の VC テキストチャットへ出す
- ホスト打診はホスト候補のチーム側の VC テキストチャットにだけ出す
- bot は VC / チャンネル / 権限 / メッセージを作成・削除・変更しない。投稿済みメッセージは掃除せず、ID を `formation_events.payload` に記録する
- **VC テキストチャットは通知と部屋コードの受け渡し専用**。ここで勝敗の話をさせない（後述）

### ホスト打診

ホスト候補のチーム側 VC テキストチャットでホストをメンションし、ボタンを出す。

```
@ホスト あなたがこの試合のホストです。
下の設定でカスタムルームを作って、ルームIDを入力してください。

  スタジアム: <固定値>
  ドラフト: <固定値>
  もちものレベル: <固定値>
  ユナイトライセンス: <固定値>

[ 部屋を作る ]  [ 今回はパスする ]
```

「パスする」は罰則なしで用意する。用意しないと無言で放置されるだけで、90秒無駄になる。

### 部屋コードの回収と配布

ホストがモーダルにコードを入力 → bot が `awaiting_code` を抜ける → red / blue 両方の VC テキストチャットへ開示。

コードはモーダル入力からだけ受ける。自由記述を読まないため、MESSAGE_CONTENT インテントも曖昧なパースも不要になる。

## 4. 報告フローとブラインドの担保

**報告は VC テキストチャットでやらない。** 他人の発言が見える場所で勝敗を報告させた時点でブラインドが壊れる。00の3章の「UIで隠すだけでは不十分」より前の段階で壊れる。

報告は Web 側のフォーム、または Discord のボタン + **ephemeral レスポンス** で受ける。botを使う場合:

- 報告ボタンを押した結果は本人にしか見えない ephemeral メッセージで返す
- 「誰が押したか」が VC テキストチャットに残らないこと（`deferred_ephemeral` で応答）
- **「◯人が報告済み」を表示しない。** 件数自体は内容を漏らさないが、拮抗している気配を読ませる材料になるし、無言の圧力になる

### スクリーンショットの扱い

00の3章「書かなかったデータは永久に取得不能」に従うなら、結果画面のスクショは全試合で任意提出させて `raw_result` に貯めておく価値がある。ただし**VC テキストチャットに貼らせてはいけない**（勝敗が写るのでブラインドが壊れる）。報告フォームの任意添付にする。

レートには使わない。後から不正の疑いが出たときの唯一の外部証拠として置いておくだけ。

## 5. 失敗経路

| 事象 | 挙動 |
|---|---|
| ホストが90秒無反応 | 次の候補へ。3人目まで |
| ホスト候補が全滅 | `abandoned`。10人全員をキューに戻す。無反応だった人に `host_no_show` を記録（レートには影響させない） |
| 部屋に人が揃わない | ホストが「不成立」を押す → `abandoned`。欠けた人に `no_show` を記録 |
| 試合中にクラッシュ・再戦した | ホストが「やり直し」を押す → 現formationを `voided` にして、同じ10人で新しいformationを起こす |
| 45分報告ゼロ | `voided`。報告ゲートは立てない |
| 報告が拮抗 | `disputed`。03の既存ルール（スクショ提出）に接続 |
| botが落ちた | **DBが正。**再起動時に未終了のformationを読み直して状態を再構築する。Discord側のメッセージIDはDBに持つ |

`voided` と `abandoned` は**報告ゲートを立てない**。試合が成立していないので、報告義務も発生しない。

## 6. スキーマ（追記専用）

00の3章の不変条件に従い、状態遷移も追記で表現する。`formations` の状態カラムを UPDATE するのではなく、イベントを積んで現在状態を導出する。

```sql
-- マッチメイカが確定させた時点で1行。以後不変
create table formations (
    id              uuid primary key,
    created_at      timestamptz not null,
    -- マッチング時点の凍結値（既存方針どおり）
    matchmaking_params_version int not null,
    predicted_win_prob real not null,
);

create table formation_players (
    formation_id    uuid not null references formations(id),
    player_id       uuid not null,
    team            smallint not null,   -- 0 or 1
    role            text not null,
    role_was_flexed boolean not null,    -- フレックス補償の入力
    mu_at_match     double precision not null,
    sigma_at_match  double precision not null,
    primary key (formation_id, player_id)
);

-- 状態遷移ログ。追記のみ。現在状態はこれの最新行から導出
create table formation_events (
    id              bigserial primary key,
    formation_id    uuid not null references formations(id),
    occurred_at     timestamptz not null,
    kind            text not null,       -- host_assigned / host_declined / host_timeout
                                         -- / code_posted / match_started / voided / abandoned ...
    subject_player_id uuid,
    payload         jsonb not null       -- 部屋コード、タイムアウト理由など生データ
);

-- 報告。1人1行、追記のみ。取り消しは打ち消しレコード
create table match_reports (
    id              bigserial primary key,
    formation_id    uuid not null references formations(id),
    player_id       uuid not null,
    reported_at     timestamptz not null,
    winning_team    smallint not null,
    raw_result      jsonb not null,      -- スクショURL含む生データ
    supersedes_id   bigint references match_reports(id)
);
```

**`formations` に `state` カラムを置かない。** 置くと必ず UPDATE したくなる。現在状態は `formation_events` の最新から求めて、必要ならマテビューかキャッシュにする。

## 7. 9/12までにやらないこと

- レーティング計算（初週の試合が終わってからオフラインで回す）
- ランキング表示（翌週でよい）
- フレックス補償のロジック（`role_was_flexed` を記録だけしておけば、後から遡って効かせられる）

記録だけ先にやっておけば、計算は後から取り返せる。それが00の3章の効き目。
