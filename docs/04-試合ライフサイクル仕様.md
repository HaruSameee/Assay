## 0. なぜこの文書が要るか

00の7章（実装順序）は「マッチメイキング → レーティング」と書いてあるが、その間に**マッチが成立してから試合が始まるまでの手順**が抜けている。ユナイトに外部APIが無い以上、部屋は人間が立てる。その人間を指名し、部屋コードを回収し、9人に配り、失敗したら畳む、という手順は自動化しないと回らない。

規模の見積もり: 同接40人で4ロビー、96人フル参加で9ロビー。1日16ラウンドとして、週末1回で **200〜300回** この手順が走る。

## 1. 状態機械

```
  matched ──► awaiting_host ──► awaiting_code ──► in_progress ──► awaiting_reports ──► confirmed
                   │                  │                                   │                 
                   │                  │                                   ├──► disputed
                   ▼                  ▼                                   │
               abandoned          abandoned                               └──► voided
```

| 状態 | 意味 | 次へ進む条件 | タイムアウト |
|---|---|---|---|
| `matched` | マッチメイカが10人を確定。formation凍結済み | VC の組を割当・通知完了 | なし |
| `awaiting_host` | ホストを指名し、承諾を待つ | 候補が**マッチ画面で**「部屋を作る」を押す | **180秒**（既定）→ 次の候補へ |
| `awaiting_code` | ホストが部屋を作り、ルーム ID を入れるのを待つ | ルーム ID が投稿される | **180秒** → 次の候補へ |
| `in_progress` | ルーム ID を9人に開示済み | 最初の報告が届く | **45分** → `voided` |
| `awaiting_reports` | 報告受付中 | 確定ルール（03参照）を満たす | 最初の報告から**30分**。確定・係争の評価は Phase 6 |
| `confirmed` | 勝敗確定。レート計算の入力になる | — | — |
| `disputed` | 報告が拮抗。スタッフ介入待ち | — | — |
| `voided` | 試合が成立しなかった。レートに影響させない | — | — |
| `abandoned` | ホスト候補が全滅、または人が集まらず解散 | — | — |

### 当日の校正対象（環境変数）

打診まわりの2つは、実装が定数を持たず環境変数から読む（`src/lifecycle/config.rs`）。

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `HOST_ACCEPT_TIMEOUT_SECONDS` | **180** | `awaiting_host` の承諾期限 |
| `HOST_CANDIDATE_LIMIT` | **3** | 打診するホスト候補の上限 |

どちらも `0` は起動で落とす。候補0人は「成立した瞬間に必ず解散」、承諾0秒は「打診した瞬間にタイムアウト」であり、設定ミスが黙って動く形になるため。

**承諾期限が90秒から180秒になった理由**: 90秒は「Discordのボタンを押すだけ」を前提にした値だった。§3 のとおり操作はサイトへ移り、候補は Discord の通知に気づいてからマッチ画面を開く。開くまでの時間を含めた値にしてある。

**ホスト候補が尽きたら `abandoned`。** 10人全員を試すのではなく、`HOST_CANDIDATE_LIMIT` 人（既定3人）まで試して駄目なら解散する。それ以上粘っても10人を拘束するだけで、次のラウンドに回したほうが早い。

## 2. ホストの選び方（要再検討）

### 現在の決定

レートが一番上の人をホストに指名する。

### この決定の問題

**負担がレートに対して単調増加する。** ランキング1位の人は、自分が参加するほぼ全てのロビーで最上位になる。つまり毎試合ホストをやることになる。上位者はこのシステムの看板であり、配信者候補であり、LFT指標として一番見られる人たちで、一番機嫌よく回ってほしい層。そこに構造的な作業税をかける設計になっている。

**レートはホスト適性の代理変数として情報を持っていない。** 実際に効くのは「いま端末の前にいるか」「回線が安定しているか」「部屋設定を間違えないか」で、レートはそのどれとも相関しない。

**部屋設定の権限がホストに乗る。** ドラフトの有無、もちものレベル、使用スタジアム、ライセンス解放状態。これが全ロビーで揃っていないと、ログ同士が比較可能でなくなる。00の3章「試合ログが唯一の正」に直撃する。設定権限を「一番強い人」に渡す理由は無い。

### 代案

**直近ホスト時刻が最も古い人（LRU）。** DBに `last_hosted_at` を1カラム足すだけ。上位への課税がゼロになり、負担が全員に均等に散る。同点はレート降順で割る。

### 決着のさせ方

`HostSelector` trait にして差し替え可能にする。既に「レーティングとマッチメイキングは trait 越しに差し替え可能」という方針があるので、そこに乗せる。デフォルトを `HighestRating` にして初週を回し、上位から苦情が出たら `LeastRecentlyHosted` に切り替える。切り替えコストが1行なら、今ここで結論を出さなくてよい。

```rust
trait HostSelector {
    /// 優先順に並べたホスト候補を返す。先頭から順に打診する
    fn candidates(&self, formation: &Formation) -> Vec<PlayerId>;
}
```

## 3. Discord側の設計

### 方針: Discord は通知だけ、操作は全部サイト

**Discord にインタラクション（ボタン・モーダル）を置かない。** ホスト打診への応答、ルーム ID の投稿、報告は、すべてマッチ画面（`/match/{formation_id}`、§3-1）の HTTP エンドポイントで受ける。

**通知を Discord に残すのは、サイトを開いていない人に「あなたの番です」を伝える手段が他に無いため。** 打診には候補あたり180秒、報告には30分の期限がある。通知が無いと、画面を開いている人だけが進行できる仕組みになる。

|  | Discord | サイト |
|---|---|---|
| 通知 | ○ | — |
| 操作 | ✕ | ○ |
| 記録の開示（割り当て表・ルーム ID） | ○ | ○ |

チャット履歴に残った旧版のボタンは Discord 側で無効化しない（bot はメッセージを消さない）。押されたら、押した本人にだけマッチ画面への行き先を返し、**状態は一切変えない**。

### VC テキストチャット

**試合ごとのプライベートスレッドは作らない。** 事前作成した `vc<N>-red` / `vc<N>-blue` の VC に付属するテキストチャットへ投稿する。専用サーバーはブースト0であり、プライベートスレッドのブースト要件に依存しないためである。

- 割り当て表、集合先、部屋設定、ルーム ID は red / blue 両方の VC テキストチャットへ出す
- **割り当て表はそのVCのチームの構成だけを載せる**（red の VC には red だけ）。両チーム分を1つの本文にして両方へ投げると、サイト側で相手のロールを隠しても意味が無くなる（§3-1）
- ホスト打診の通知はホスト候補のチーム側の VC テキストチャットにだけ出す
- bot は VC / チャンネル / 権限 / メッセージを作成・削除・変更しない。投稿済みメッセージは掃除せず、ID を `formation_events.payload` に記録する
- **VC テキストチャットは通知とルーム ID の開示専用**。ここで勝敗の話をさせない（後述）

### 招集チャンネル

公開の招集チャンネルには、成立の通知を**チームごとに1通ずつ**出す。1通に両チームを入れると、相手の顔ぶれと行き先が同じ場所に並ぶ。

ホストが決まったら、招集チャンネルにも「ホストは @X です。サイトで部屋を作ってルーム ID を入力してください」を出す。**ホストは相手チームの人にも伝える** — 誰が部屋を建てたか分からないと、入れなかったときに聞く相手が分からない。ホストのロールは出さない。候補が次に移ったら、その旨も同じチャンネルに出す。

### ホスト打診

ホスト候補のチーム側 VC テキストチャットでホストをメンションする。**ボタンは無い。**

```
**[vc3] 2026-09-12 21:00 JST · match-xxxxxxxx**
@ホスト さん、部屋の作成をお願いできますか？（候補 1/3）
マッチ画面で「部屋を作る」か「今回はパスする」を選んでください: https://match.aynm.dev/match/<id>
```

「パスする」は罰則なしで用意する。用意しないと無言で放置されるだけで、承諾期限（既定180秒）を丸ごと無駄にする。

部屋設定（スタジアム・ドラフト・もちものレベル・ユナイトライセンス）は、割り当て表の「部屋設定」チェックリストとマッチ画面の両方に出る。

### ルーム ID の回収と配布

ホストがマッチ画面の入力欄に入れる → `code_posted` が積まれる → red / blue 両方の VC テキストチャットへ開示。

**自由記述は読まない。**入力はサイトのフォームからだけ受けるので、MESSAGE_CONTENT インテントも曖昧なパースも要らない（モーダルを使っていた頃と同じ理由が、そのまま HTTP に移っただけ）。

開示のメッセージに**参加者10人のメンションは付けない**。招集チャンネルで既に通知しており、重複する。ホストのメンションだけ残す — 1人なので通知の重複にならず、部屋に入れなかったときに誰へ聞けばよいかが分かる。

**打ち直しは新しいイベントとして通る。**冪等キーはルーム ID の内容から作るので、違う値を入れれば必ず別のイベントになり、両 VC の開示も更新される（00 §5「状態ベースの冪等にすると部屋コードの打ち直しを黙って捨てる」）。

### 3-1. マッチ画面（`/match/{formation_id}`）

成立から確定まで、**同じ URL の1枚**。キュー画面と同じ10秒ポーリングで中身だけが切り替わる。

常に出すもの: 両チーム（左右）、各チームの割り当て VC、参加者のトレーナー名と現在のレート、自分の強調、ホストが誰か、部屋設定のチェックリスト。

**出さないもの:**

- σ、レート調整の内訳、他人の戦績
- **他人の報告状況。件数も含む**（§4）
- **相手チームのロール割り当て**

相手のロールを隠すのは、部屋に入るまでの数分で相手の構成に合わせたドラフト準備をされるのを防ぐため。ゲーム内のドラフトが始まれば分かるので、隠せるのはその数分だけである。レートは公開方針（00 §4「σは公開する」「ランキングは公開」）なので隠さない — ランキングから引ける情報を隠しても意味がない。

|  | 自チーム | 相手チーム |
|---|---|---|
| 参加者名 | ○ | ○ |
| レート | ○ | ○ |
| ロール | ○ | **✕** |

実装では、自チームと相手チームで**型を分けてある**（`TeammateView` / `OpponentView`）。相手側の型に `role` フィールドが無いので、HTML にもレスポンスにも出しようがない。

**通知の送出はマッチ画面からは行わない。** HTTP はイベントを積むだけで、Discord への投稿は既存の再開ループ（5秒スキャン）が DB の状態から出す。復帰の入口を2つ作らないため（00 §7 の Phase 5 申し送り）で、プロセスが落ちても続きから進む。投稿済みかどうかもログから導出する（プロセス内のフラグに持たない）。

副作用として、**ルーム ID を送信してから VC に出るまで最大5秒の遅れがある**。マッチ画面の全員には次のポーリングで出る。

## 4. 報告フローとブラインドの担保

**報告は VC テキストチャットでやらない。** 他人の発言が見える場所で勝敗を報告させた時点でブラインドが壊れる。00の3章の「UIで隠すだけでは不十分」より前の段階で壊れる。

**報告はマッチ画面で受ける。**「赤の勝ち」「青の勝ち」「無効試合」の3択（`draw` は選択肢に入れない。無効試合に寄せる）。Discord に残すのは、ルーム ID 開示後に両 VC へ出す催促だけ。

```
**[vc3] 2026-09-12 21:00 JST · match-xxxxxxxx**
試合が終わったら、マッチ画面で結果を報告してください: https://match.aynm.dev/match/<id>
報告内容は他の参加者には表示されません。
```

催促にはボタンもメンションも付けない。勝敗の語も出さない（選択肢はサイトにある）。

ブラインドの制約は「他人の報告内容が、まだ報告していないプレイヤーに到達する経路を作らない」（00 §3-5）。したがって:

- **他人の報告状況を一切出さない。「◯人が報告済み」も出さない。** 件数自体は内容を漏らさないが、拮抗している気配を読ませる材料になるし、無言の圧力になる。「9人報告済み、自分だけ未報告」が見えると、00 §5 が却下した「他9人に人質を取られる」構造が別の形で戻る
- 自分が報告したかどうかだけを出す。報告後は「受け付けました。確定を待っています」
- `disputed` のときも他人の報告内容を出さない
- **HTML にもAPI のレスポンスにも含めない。**DOM を見れば分かる形にしない

実装では、画面に渡す値の型（`MatchView`）に**件数のフィールドを作っていない**。あるのは自分の報告済みフラグと、確定後の自分の増減だけ。

確定判定は既存のロジックを変えていない（入口が Discord から HTTP に変わっただけ）。報告した人の中での全員一致で `confirmed`、全員が「無効試合」で一致なら `nullified`、割れていれば `disputed`。10人全員が報告済みで一致していれば即確定、そうでなければ最初の報告から30分後に評価する。訂正は追記で、**確定判定は最新の報告・一致率は最初の報告**（00 §5）。

> **当日の運用で把握しておくこと**: 10人全員が報告していても**一致していなければ即座には確定しない**。多数決を採らないため（00 §5「5-4のような非対称な報告数は正常系」）、割れた試合は最初の報告から30分後の評価まで待つ。

### スクリーンショットの扱い

00の3章「書かなかったデータは永久に取得不能」に従うなら、結果画面のスクショは全試合で任意提出させて `raw_result` に貯めておく価値がある。ただし**VC テキストチャットに貼らせてはいけない**（勝敗が写るのでブラインドが壊れる）。報告フォームの任意添付にする。

レートには使わない。後から不正の疑いが出たときの唯一の外部証拠として置いておくだけ。

## 5. 失敗経路

| 事象 | 挙動 |
|---|---|
| ホストが承諾期限（既定180秒）まで無反応 | 次の候補へ。`HOST_CANDIDATE_LIMIT` 人目まで |
| ホスト候補が全滅 | `abandoned`。10人全員をキューに戻す。無反応だった人に `host_no_show` を記録（レートには影響させない） |
| 部屋に人が揃わない | ホストが「不成立」を選ぶ → `abandoned`。欠けた人に `no_show` を記録 |
| 試合中にクラッシュ・再戦した | ホストが「やり直し」を選ぶ → 現formationを `voided` にして、同じ10人で新しいformationを起こす |
| 45分報告ゼロ | `voided`。報告ゲートは立てない |
| 報告が拮抗 | `disputed`。03の既存ルール（スクショ提出）に接続 |
| プロセスが落ちた | **DBが正。**再起動時に未終了のformationを読み直して状態を再構築する。Discord側のメッセージIDはDBに持ち、**投稿済みかどうかもログから導出する**（プロセス内のフラグに持たない） |

`voided` と `abandoned` は**報告ゲートを立てない**。試合が成立していないので、報告義務も発生しない。

> **この表のうち、9/12 時点で入口が無いもの**（マッチ画面への移行とは無関係に、以前から未実装）:
> 「部屋に人が揃わない」（`AbandonReason::NotEnoughPlayers` を積む経路が無い）と
> 「試合中にクラッシュ・再戦」（`voided` を積むのは報告ゼロの期限切れだけ）。
> 当日この2つが起きたら、運営が `disputed` 経由で裁定するか、放置して45分の
> `voided` に落とすことになる。マッチ画面に足すなら §3-1 の3択の隣。

## 6. スキーマ（追記専用）

00の3章の不変条件に従い、状態遷移も追記で表現する。`formations` の状態カラムを UPDATE するのではなく、イベントを積んで現在状態を導出する。

```sql
-- マッチメイカが確定させた時点で1行。以後不変
create table formations (
    id              uuid primary key,
    created_at      timestamptz not null,
    -- マッチング時点の凍結値（既存方針どおり）
    matchmaking_params_version int not null,
    predicted_win_prob real not null,
);

create table formation_players (
    formation_id    uuid not null references formations(id),
    player_id       uuid not null,
    team            smallint not null,   -- 0 or 1
    role            text not null,
    role_was_flexed boolean not null,    -- フレックス補償の入力
    mu_at_match     double precision not null,
    sigma_at_match  double precision not null,
    primary key (formation_id, player_id)
);

-- 状態遷移ログ。追記のみ。現在状態はこれの最新行から導出
create table formation_events (
    id              bigserial primary key,
    formation_id    uuid not null references formations(id),
    occurred_at     timestamptz not null,
    kind            text not null,       -- host_assigned / host_declined / host_timeout
                                         -- / code_posted / match_started / voided / abandoned ...
    subject_player_id uuid,
    payload         jsonb not null       -- 部屋コード、タイムアウト理由など生データ
);

-- 報告。1人1行、追記のみ。取り消しは打ち消しレコード
create table match_reports (
    id              bigserial primary key,
    formation_id    uuid not null references formations(id),
    player_id       uuid not null,
    reported_at     timestamptz not null,
    winning_team    smallint not null,
    raw_result      jsonb not null,      -- スクショURL含む生データ
    supersedes_id   bigint references match_reports(id)
);
```

**`formations` に `state` カラムを置かない。** 置くと必ず UPDATE したくなる。現在状態は `formation_events` の最新から求めて、必要ならマテビューかキャッシュにする。

## 7. 9/12までにやらないこと

- レーティング計算（初週の試合が終わってからオフラインで回す）
- ランキング表示（翌週でよい）
- フレックス補償のロジック（`role_was_flexed` を記録だけしておけば、後から遡って効かせられる）

記録だけ先にやっておけば、計算は後から取り返せる。それが00の3章の効き目。
