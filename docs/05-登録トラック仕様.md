# 05-登録トラック仕様（改訂）

**作成**: 2026-09-05
**改訂理由**: 初版はDiscord完結を推していたが、キューUIをWebに置く以上OAuthは必須。前提が誤っていた
**スコープ**: 9/12に必要な認証と登録。ランキング表示・プレイヤーページは範囲外

---

## 0. 先にやること（リードタイムがある）

**これが一番のボトルネックです。実装ではなくDNSと証明書の待ち時間なので、今日か明日に着手してください。**

1. **ドメインを取得**する
2. **DNSをVPSに向ける**（伝播待ちがある）
3. **TLS証明書を発行**する（Let's Encrypt。HTTP-01ならDNSが引けてから）
4. **Discord Developer Portal にリダイレクトURIを登録**する。完全一致なので、本番URLを先に確定させること

OAuthのリダイレクトURIは**HTTPSの公開URL**でなければなりません。ここが揃うまで、OAuthの実装はローカルでしか検証できません。実装は進められますが、通しの確認が9/11まで倒れると詰みます。

## 1. 認証方式

Discord OAuth2 の認可コードフロー。

```
GET https://discord.com/oauth2/authorize
    ?client_id=<APP_ID>
    &redirect_uri=<登録済みURI>
    &response_type=code
    &scope=identify
    &state=<CSRFトークン>

→ コールバックで code を受け取る
→ POST https://discord.com/api/oauth2/token でアクセストークンに交換
→ GET https://discord.com/api/users/@me で Discord ユーザーIDを取得
```

**scope は `identify` だけで足ります。**`guilds` を足すとサーバー所属を確認できますが、それはbot側から確認したほうが安いです（後述）。要求するスコープは少ないほど、登録画面の同意ハードルが下がります。

### セッション

**署名付きCookieにしてください。**セッションストアを立てない。9/12までなら、有効期限付きの署名Cookieで足ります。サーバー側の状態が増えず、リカバリの考慮も要りません。

axum なら `axum-extra` の `SignedCookieJar`。ログアウトの即時失効が要るようになったら、そのとき Postgres のセッションストアに移せます。

### CSRF

`state` パラメータを生成し、**短命なCookieに入れて**コールバックで突き合わせてください。

### Cookieの属性（ここを間違えると本番だけ落ちます）

- `HttpOnly`
- `Secure`
- **`SameSite=Lax`**

`Strict` にしないでください。OAuthのコールバックは discord.com からのトップレベル遷移なので、`Strict` だと `state` Cookieが送られず、**ローカルのhttpでは通って本番のhttpsで落ちます。**Phase 3 の `FOR UPDATE` と同じ形の、本番でしか出ないバグです。

### ギルド所属の確認

登録後、**bot側から**そのDiscordユーザーがAssayサーバーにいるかを確認してください。いなければ「サーバーに参加してください」と返します。

理由は、いなければbotがスレッドに追加できず、マッチが成立しないからです。OAuthのスコープを増やすより、bot APIで1回問い合わせるほうが安い。

## 2. スキーマ

`players` は Phase 1 で最小構成（`id` / `discord_user_id` / `created_at`）があるので、列を足します。

```sql
alter table players add column trainer_name  text;
alter table players add column status        text not null default 'active';
alter table players add column registered_at timestamptz;
-- status は 'active' / 'suspended'
```

`players` は追記専用ではありません。トレーナー名の変更もBANも通常のUPDATEでよく、**UPDATE/DELETE禁止の対象4テーブルには引き続き含めません。**

**申告レートは可変列にしないでください。**これはレートseedの入力で、seedはレートの導出経路の一部です。可変列に置いて上書きした瞬間、過去のrecomputeが再現しなくなります。

```sql
create table player_declarations (
    id           bigserial primary key,
    player_id    uuid not null references players(id),
    declared_at  timestamptz not null,
    rank         text not null,
    rating       int,
    raw          jsonb not null
);

create index player_declarations_player_idx on player_declarations (player_id, id);
```

追記専用です。**REVOKEとトリガーの対象に加えてください。**申告し直しは新しい行で、seedは「その時点で最新の申告」から導出します。

## 3. 登録フォーム

ログイン後の1ページ。

- トレーナー名（ゲーム内名）
- 本家ランク（ビギナー〜レジェンドの選択）
- 本家レート（マスター／レジェンドのとき）

送信で `players` を作成または更新し、`player_declarations` に必ず1行追記します。

**レジェンド未満でも登録は受け付けて記録してください。**参加資格が無い旨は返しますが、あとで上がったら再申告すればよく、「何人が資格未満で弾かれたか」は次シーズンの足切りを決める数字になります。生データを捨てない原則そのままです。

参加資格の検証は既存方針どおり**自己申告＋トレーナー情報の公開**です。スタッフの目視確認は例外対応にだけ使います。

## 4. キューのゲート

キューに入れる条件を2つに分けてください。

- **登録ゲート**: 未登録 / `status = 'suspended'` / 直近の申告がレジェンド未満 → 入れない
- **報告ゲート**: 未報告のformationを持つ → 入れない（既存）

**1つのフラグに畳まないこと。**畳むと、キュー画面で「なぜ入れないのか」を説明できなくなります。

## 5. キューUIとの関係（未確定・要決定）

この仕様書は認証と登録までです。**キューUI自体はまだどこにも仕様がありません。**必要なのは:

- ロール選択（最大3つ、優先度付き）
- レート範囲の指定（下方向のみ、最低50 / 初週デフォルトは300〜400を推奨）
- 「現在あなたの範囲内でキュー中: N人」の表示
- キュー参加 / 取消
- マッチ成立の通知（Discordのbotも鳴らすので、Web側は「マッチしました、Discordを見てください」で足りる）

ライブ更新は5秒ポーリングで足ります。この規模でSSEやWebSocketを入れる理由はありません。

認証基盤ができれば、この5つは1日規模のはずです。

## 6. 運用

- **登録受付は9/10までに開ける。**当日に開けると初回のキューが登録待ちで埋まります
- 既に96人が名乗り出ているので、告知でログインURLに流す導線が要ります
- トレーナー名は他の参加者から見える前提で告知してください。自浄が働く前提がこれです

## 7. やらないこと

- セッションストア（署名Cookieで足りる）
- スクリーンショットによる資格検証
- ランキング表示、プレイヤーページ
- 申告レートの妥当性チェック。過少申告は初日のマッチ品質を落としますが、μ+σ で数試合のうちに収束します
