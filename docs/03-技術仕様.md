## 2. ドメインモデル

### 2.1 スコープ

- **1キュー = 1試合で完結する連続マッチメイキング**
- トーナメント / ラウンド / ブラケット / Swiss の概念は**存在しない**
- 5v5

### 2.2 エントリー単位

| フェーズ | 対応 |
|---|---|
| 初動 | solo のみ |
| 将来 | solo / duo |
| 当面見送り | trio |
| 非対応 | フルパ5人 |

**注**: 構成の非対称（片方だけパーティを含む等）は例外処理ではなく**主要経路**として扱う。連続キューでは (3+2) vs (3+2) のような綺麗な組み合わせは滅多に揃わない。

### 2.3 参加資格

- 本家レジェンドランク以上
- 確認: トレーナー情報の公開が必須。非公開希望者は運営が個別認証
- **未調査**: UniteAPI のデータ取得手法が使えるか

### 2.4 想定規模

| 指標 | 値 |
|---|---|
| 参加予定者（2026-09-04、宣伝10時間時点） | 96人 |
| 想定登録・同接上限 | 200人程度 |
| 想定同時キュー | 20〜30人 |

### 2.5 開催時間

土日 21:00〜25:00。この時間外はキュー受付を行わない。

## 3. アーキテクチャ不変条件

**これらは他の判断より優先される。破る変更は入れない。**

### 3.1 試合ログが唯一の正・追記専用

- UPDATE / DELETE しない
- 取り消しは**打ち消しレコード**で表現する
- `player_ratings` の直接UPDATEは行わない。すべて recompute の入力となる追記レコードで表現する
  - `match_result_corrections`
  - `rating_adjustments`

### 3.2 レーティングは導出値

試合ログから完全に再構築できること。レーティングを一次データとして持たない。

### 3.3 recompute が唯一の計算経路

- 全履歴再計算を唯一の経路とする
- **インクリメンタル更新を作らない**
- recompute は常に「**現行の** rating params」を全履歴に適用する
- 当時のparamsで再生はしない。したがって `param_activations` テーブルは**不要**

### 3.4 生データを捨てない

- 報告された生データを `raw_result` JSONB で保持
- 理由: 外部APIが無いため、書かなかったデータは永久に取得不能

### 3.5 マッチング時点の状態を凍結

formation 側に以下を保存する。

- 各プレイヤーの μ・σ
- matchmaking params version
- 予測勝率

### 3.6 差し替え可能性

- レーティングとマッチメイキングは **trait 越しに差し替え可能**
- パラメータはすべてバージョン付き
- `audit_log` 必須

## 4. レーティング

### 4.1 表現

プレイヤーの実力を**分布**で持つ。

| 記号 | 意味 |
|---|---|
| `μ` | 実力の推定値 |
| `σ` | その推定の不確かさ（標準偏差） |

性質:

- σが大きい → 1試合の結果で大きく動く
- σが小さい → あまり動かない
- 試合をするとσは縮む
- 試合をしない期間があるとσは膨らむ
- 対戦相手のσも更新式に入る（σの大きい相手との対戦は情報量が少ないので動きが小さい）

### 4.2 アルゴリズム候補【未選定】

| 候補 | 特徴 | Rust実装 |
|---|---|---|
| **Weng-Lin (OpenSkill)** | チーム戦向けの逐次更新。TrueSkillの特許非依存版 | `skillratings` crate（Elo/Glicko/Glicko-2/TrueSkill/Weng-Lin を収録、team vs team・multi-team 対応、デフォルト依存ゼロ）、`openskill` crate |
| **WHR (Whole-History Rating)** | 全履歴を使って一括で最尤推定。逐次更新より少ない試合数で精度が出る | `whr` crate |

**WHRを検討する理由**: 「追記専用ログから全履歴recompute」という 3.3 の設計思想と完全に一致する。計算コストは重いが、200人規模なら誤差。低試合数設計との相性も良い。

### 4.3 スケール

- 内部はライブラリの生の値をそのまま持つ（Weng-Lin なら μ=25, σ≈8.33 が既定）
- **表示のみ変換する**（例: `表示値 = μ × 60` で1500スタート）
- 表示倍率は「σが収束した後の1試合の増減が体感的に妥当な幅になる」ように選ぶ

**注意**: 「1試合の増減を10〜14にする」は設定値ではない。σから出てくる。設定するのは表示倍率のみ。

### 4.4 初期値

初期値は一律1500（内部 μ=25、σ=25/3）。実績に基づく例外的な調整は、表示スケールで保存した `rating_adjustments` の追記ログをrecomputeの入力に含める。自動seedは実装しない。

### 4.5 入力

**勝敗のみ**。KO数・与ダメージ・被ダメージ等のパフォーマンス指標は参照しない。

### 4.6 序盤補正

**入れない**。σが同等の機能を持つため。

### 4.7 シーズン

- シーズンリセットは**しない**。レートを書き換える操作は存在しない
- 代わりに**導出の起点（シーズン境界）を追記する**。境界より前の試合と調整は集計に入らなくなるが、ログは1行も消えない
- 境界を入れると、**μ・σとも新シーズンの起点から導出する**。σは持ち越さない
- 境界が1本も無い状態が既定で、そのときは全履歴が対象

### 4.8 パーティ有利【将来】

係数ではなく**シナジー項**で表現する。

```
チーム強度 = Σμ + s3/s2
```

- 当初案（トリオ 0.8 / デュオ 0.9 / ソロ 1.0 の係数）は撤回
- **ソロ限定の間は s2・s3 を推定するデータが1件も出ない**。デュオ解禁後も同定できるのは s2 のみ
- 設計には穴を空け、実装は後回しでよい
- **未決**: シナジー項の初期値とキャリブレーション方法
- **未決**: 固定パーティのσが縮まりすぎる問題

## 5. マッチメイキング

### 5.1 ロールキュー

- カテゴリ: 上/下レーン、中央キャリー、上下キャリーの3つ
- プレイヤーは**最大3つ**まで希望を出せる
- **優先順位**を付けられる
- 1つだけ選ぶことも可能

### 5.2 フレックス補償【推奨・未確定】

「前回フレックスで埋められた人は、次回は第1希望を優先」というフラグを持つ。

実装コスト: プレイヤーごとに「前回フィルされたか」のフラグ1個。

**これを入れない場合の予測される帰結**: 全員が希望を1つしか選ばない均衡に落ち、5.1 の複数選択が形骸化する。

### 5.3 レート範囲【未決】

2案あり、決着していない。詳細は `02-設計判断ログ.md` B-3。

- 案1: ユーザーが±で指定
- 案2: システムが自動拡大（デフォルト±100、待ち時間で拡大、上限±400、ユーザーは広げる方向のみ）

**どちらを採るにせよ実装するもの**: キュー画面に「現在あなたの範囲内でキュー中: N人」を表示する。

### 5.4 確定

- マッチは**自動で確定**する
- **相手を見てからのキャンセルは不可**

## 6. 報告・係争

### 6.1 報告

- **10人全員**が報告する
- **ブラインド**: 報告内容は、それを書いたプレイヤー以外のクライアントに到達してはならない
  - UIで隠すだけでは不十分。**APIレベルで遮断する**
  - サーバ内部の評価器（確定ルール）は全報告を読んでよい。ただしその戻り値は判定結果（confirmed / disputed / 保留）のみであり、報告の内容・内訳・件数を含まない
  - **報告 API のレスポンスは受理の可否だけ**。確定状態、`disputed` かどうか、フラグが立ったかどうかは返さない。返すと「適当に報告して反応を見てから訂正する」探り方が成立する
- 訂正は `supersedes_id` を持つ新しい行で表現する。同じプレイヤー・同じ formation の報告に限り、1つの報告を打ち消せるのは1件だけ（訂正チェーンは分岐しない）

### 6.2 確定ルール

| 状況 | 挙動 |
|---|---|
| 全一致 | 確定 |
| 少数1件のみ不一致 | 自動確定 ＋ 不一致者にフラグ ＋ 通知（ブロックはしない） |
| 拮抗 | `disputed` |

**多数決は採らない**。5-4 のような非対称な報告数は正常系。

**`confirmed` 後に届いた遅れた報告で確定判定を再実行しない。** `confirmed` は lifecycle の終端。遅れた報告は受け付けるが（未報告者の報告義務は確定後も残る）、報告一致率の入力にだけなる。

**未決**: 確定に必要な最小報告件数、タイムアウト時の挙動。（厳密に詰めるのは「キリがない」として妥協する方針）

### 6.3 disputed の解決

- フラグを立て、勝敗結果のスクリーンショットを提出させる
- **勝っている側が開示すれば足りる**
- 負けている側が全員非開示でもブロックにはならない

### 6.4 報告ゲート

- 未報告の formation を持つプレイヤーは**キューに並べない**
- 解除条件は「**自分が報告したこと**」
  - 「確定したこと」を条件にすると、他9人に人質を取られるため
- `disputed` 中はゲート解除済み扱い

### 6.5 不正対策の方針

- **検証の完全性は目指さない**
- 5人規模の共謀は「割に合わない」と判断し、専用の対策コストはかけない
- 残余リスクの補い方:
  - スタッフの手作業
  - プレイヤーごとの**報告一致率**の記録
    - 一致率は**各プレイヤーの最初の報告**で測る（追記専用なので最初の報告は消えない）。訂正（`supersedes_id`）は勝敗判定にだけ効き、指標には効かない。そうしないと、フラグが立ってから多数派に合わせ直すことで指標をすり抜けられる

**前提条件**: この方針は金銭が絡まないことを前提としている。賞金導入時は再検討が必要。

## 7. 表示・公開

### 7.1 ランキング

**2本立て**にする。

| 種別 | 対象 | デフォルト |
|---|---|---|
| 確定ランキング | σが閾値以下のプレイヤー | ✅ |
| 全体ランキング | 暫定を含む全員 | |

- ソートキーは **μ（実レート）のみ**
- `μ − 3σ` のような変換はしない（単調性が失われるため）
- ランキングは序盤から公開する

### 7.2 詳細情報の公開

σを含む内部値を**隠さず公開**する。

詳細ページに出すもの:

- μ（実レート）
- σ（確度）
- 試合数
- 推移グラフ
- 対戦履歴

3.1〜3.3 により、詳細ページは実質**ログの再生ビュー**として実装できる。

### 7.3 アルゴリズムの公開

レーティングの計算方法を公開する。したがって**説明可能性が実装要件**になる。手作りの補正を積み上げると補正同士が干渉して説明不能になるため、1つの機構で複数の挙動を説明できる設計を優先する。

## 付録: 開幕時点で決めなくてよいもの

3.2 と 3.3 により、**レーティングのアルゴリズムとパラメータは開幕時点で確定させる必要がない**。

最初の2週間のログが溜まってからパラメータを調整し、過去分ごと引き直せる。普通のラダーでは「一度出したレートは動かせない」が制約になるが、この設計はそこを最初から外してある。

したがって実装の優先順位は:

1. ログの記録（3.1、3.4）
2. 報告フロー（6章）
3. マッチメイキング（5章）
4. レーティング計算（4章）— 暫定パラメータでよい
5. 表示（7章）

の順で、4 の精度は後から取り返せる。
