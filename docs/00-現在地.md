## 1. これは何か

ポケモンユナイト（5v5）の**非公式ランクマッチシステム**。名前は **Assay**。レジェンドランク以上限定で、決まった曜日・時間に集まってソロで潜り、独自レートが付く。

リポジトリ `unite-matchsystem`（GitHub Private）。Rust / axum / sqlx（ORM不使用）/ PostgreSQL。VPSでホスティング。ドメインは `match.aynm.dev`。

**目的は試合数を稼がせることではない。** 中堅層以上が中堅層同士で遊べる場、中堅層が評価される場、大会前期間のLFT用の指標。この3つ。

> **未決**: 「中堅層」の定義がどこにも書かれていない。参加資格はレジェンド以上だが、レジェンドは本家の最上位ランクなので、外から見ると「中堅層向け」と矛盾して見える。大会シーンの中堅という意味なら整合するが、01を読む非技術の協力者は「ランク中位」と読む。**宣伝を打つ前に1行定義を入れること。**

## 3. 壊してはいけないもの

**他の判断より優先される。これに反する変更は入れない。**

1. **試合ログが唯一の正・追記専用** — UPDATE/DELETE しない。取り消しは打ち消しレコード。`player_ratings` の直接UPDATEもしない
2. **レーティングは導出値** — 試合ログから完全再構築できること
3. **recompute が唯一の計算経路** — インクリメンタル更新を作らない。常に現行paramsを全履歴に適用
4. **生データを捨てない** — `raw_result` JSONB。外部APIが無いので、書かなかったデータは永久に取得不能
5. **報告はAPIレベルでブラインド** — 正確には「他人の報告内容が、まだ報告していないプレイヤーに到達する経路を作らない」。サーバ内部の評価器が全報告を読むのは自由。制約は外に出す形のほう
6. **追記専用のシステムは、壊れたデータで停止せず劣化して動き続ける** — 不正なイベントを消せない以上、`derive_state` が失敗すると formation が二度と読めなくなる。`apply` はINSERT前検証用（Errを返してよい）、`derive_state` は `(状態, Vec<Anomaly>)` を返す

**2と3の効き目**: レーティングのアルゴリズムとパラメータを**開幕時点で確定させる必要がない**。ログさえ正しく貯めれば、後から調整して過去分ごと引き直せる。実装の優先順位はこの事実から決まる。

**ただし境界がある**: recompute の対象は**レーティングだけ**。勝敗の確定は導出値ではなく追記された事実であり、確定ルールを変えても過去の勝敗は引き直さない。

## 4. 確定していること

### レーティング

- 表現は **μ + σ**（分布で持つ）。固定Kは不採用
- σは**公開**する。ランキングは「確定（σ小）／全体」の2本立て、デフォルトは確定
- アルゴリズムは未選定。Weng-Lin（OpenSkill）が候補。**チームWHRの自前実装も可**（コストを払って取る方針）
- 内部はライブラリの生の値で持ち、**表示のみ変換**（例: μ × 60 で1500スタート）
- 内部レートは作らない。オポも入れない。序盤の増減補正も入れない
- **初期値は一律1500。**実績考慮の加算は `rating_adjustments` に追記して運営が手動で行う
- **初週は固定増減方式**（07 §2）。μ+σ は初週後に同じログへ流して比較する
- 配信者への初期レート加算なし。サポート/タンクへの加点もなし
- パフォーマンス指標はレートに入れない

### マッチング・キュー

- 参加資格は本家**レジェンド以上**
- エントリーは**初動ソロ限定**。解禁してもデュオまで
- **ロールキュー**。希望は最大3つ、優先度付き
- ロールは5つ: `top_carry` / `top_support` / `jungle` / `bot_carry` / `bot_tank`
- チームは **red / blue**（textで持つ）
- マッチング範囲は上方向 **+95固定**。下方向はデフォルト **-95** で、ユーザーが **-200まで**広げられる（07 §3）
- キュー画面に「現在あなたの範囲内でキュー中: N人」を出す
- マッチは自動確定。相手を見た後のキャンセル不可
- フレックス補償（前回フィルされた人は次回第1希望を優先）は準確定

### 試合ライフサイクル

- **Discord は通知だけ、操作は全部サイト**（04 §3）。ホスト打診への応答・ルーム ID の投稿・報告はすべてマッチ画面（`/match/{formation_id}`）で受ける。Discord にボタンもモーダルも置かない
- **通知は Discord に残す。**サイトを開いていない人に「あなたの番です」を伝える手段が他に無い。打診には候補あたり180秒、報告には30分の期限があり、通知が無いと画面を開いている人だけが進行できる仕組みになる
- ホストは**レート最上位**を指名（`HostSelector` trait で差し替え可能）
- ロビーはユーザーが建てる。botは呼び出しと連絡のみ
- 連絡は**VCのテキストチャット**。プライベートスレッドは使わない
- VCは**事前作成の固定プール**。`vc1-red` 形式で10組（仮）。公開。割り当てはLRU
- 部屋設定: 大会モード / ドラフト3枠ban / マップはランクマ準拠（`kyogre` or `groudon`）/ サーバー AS02 / 他デフォルト
- ルーム ID はマッチ画面の入力欄で受ける。自由記述を読まない（MESSAGE_CONTENT インテント不要）
- **マッチ画面で相手チームのロールを出さない。**参加者名とレートは出す（レートは公開方針。ランキングから引けるものを隠しても意味がない）。Discord の割り当て表と招集もチームごとに分ける（04 §3-1）
- 打診の期限と候補人数は環境変数（`HOST_ACCEPT_TIMEOUT_SECONDS` 既定180 / `HOST_CANDIDATE_LIMIT` 既定3）。当日の校正対象
- 報告の一致率は**各プレイヤーの最初の報告**で測る

### 登録・認証

- **Discord OAuth**（scope は `identify` のみ）
- セッションは署名付きCookie。ストアを立てない
- Cookie は `HttpOnly` / `Secure` / **`SameSite=Lax`**（Strict にするとOAuthコールバックで state が落ちる）
- **Cookie の Domain は `match.aynm.dev` に限定**する。`.aynm.dev` にすると個人サイトと共有される
- 参加資格は自己申告＋トレーナー情報の公開。スタッフの目視確認は例外対応のみ
- 申告レートは可変列に置かず、`player_declarations` に追記する

### インフラ

- Discordは**専用サーバー**（illusion内ではない）
- botは**新規アプリケーション**（ayanamist-bot とは別）。プロセスはaxumと同一バイナリ、DBプール共有
- **追記専用がデフォルト**。実スキーマの対象は `formations` / `formation_players` / `formation_events` / `match_reports` の4テーブル。既定権限は SELECT / INSERT のみ。可変にしたいテーブルだけ `ops/app_role.sql` が読み込む `ops/app_privileges.sql` の許可リストに足す（現在は `players` / `roles`）。所有者にも効く `forbid_update_delete` トリガーで二重化する
- `match_results` / `player_declarations` は**未実装**。それぞれの実装フェーズで DDL と追記専用トリガーを同時に追加する。`tests/schema.rs` が全アプリテーブルの権限とトリガーを両方向に検査し、どちらかの不足・余分な更新権限・無効なトリガーで CI を落とす。`_sqlx_migrations` は管理用として検査を分け、アプリにはアクセスを与えない
- 本番ロールは `assay_migrator` / `assay_app` に分離する。マイグレーションと権限設定は前者、アプリの `DATABASE_URL` は後者。マイグレーションごとに `ops/app_role.sql` を再実行する
- 直列化は `pg_advisory_xact_lock`

## 5. 蒸し返さないこと

**議論済み。結論と一行理由。再検討するならこの理由を否定してから。**

### 設計

- **固定Kには戻さない** — 試合数の分散が大きすぎて単一のKが選べない（常連は100試合超、tailは3試合）
- **序盤の増減補正は入れない** — σが同じ機能を持つ
- **配信者に初期レートを加算しない** — 強さの情報ではないのでσを下げる根拠がなく、μだけ上げても数試合で消える
- **サポート/タンクにレート加点しない** — 効く大きさならファームされ、ファームされない大きさなら供給問題が解けない
- **`μ − 3σ` を表示値に使わない** — 単調でない。負けてσが縮むと表示が上がる
- **パフォーマンス指標をレートに入れない** — 全部自己申告になり、他9人がクロスチェックできない
- **マッチ確定後のキャンセルを可能にしない** — σ公開と組み合わさると、σの大きい新規が体系的に避けられる
- **多数決は採らない** — 5-4のような非対称な報告数は正常系
- **報告ゲートの解除条件を「確定」にしない** — 他9人に人質を取られる
- **賞金を安易に足さない** — 不正対策コストをかけない方針は、金銭が絡まないことが前提

### 実装

- **`SELECT ... FOR UPDATE` は使わない** — PostgreSQLの仕様上、対象テーブルのUPDATE権限を要求する。REVOKEしている以上、**本番でのみ 42501 で落ちる**
- **`derive_state` を失敗させない** — 3章6のとおり
- **冪等は「同一 idempotency_key のみ no-op」** — 「状態が既に反映済みなら no-op」にすると、同一種別で payload が違うイベント（部屋コードの打ち直し）を黙って捨てる
- **recompute の対象はレーティングだけ** — 3章の但し書きのとおり
- **報告一致率は最初の報告で測る** — 訂正で多数派に合わせられると、虚偽報告を捕まえる指標を虚偽報告者だけがすり抜ける
- **プライベートスレッドは使わない** — ブーストLevel 2要件について情報が食い違っており、専用サーバーはブースト0。依存自体を捨てる
- **Discord に操作を戻さない** — 進行の状態が2か所に分かれ、ブラインドの担保も ephemeral の挙動に依存する。操作はマッチ画面に集約する（04 §3）
- **通知を Discord から外さない** — サイトを開いていない人に「あなたの番です」を伝える手段が他に無い。外すと、画面を開いている人だけが進行できる仕組みになる
- **マッチ画面から Discord を呼ばない** — 復帰の入口が2つになる。HTTP はイベントを積むだけにし、通知は既存の再開ループが DB の状態から出す（7章 Phase 5 の申し送り）
- **テストのアプリ操作はアプリ用ロールで走らせる** — CI の通常の `DATABASE_URL` は `assay_app`。`sqlx::test` が隔離 DB とフィクスチャを準備する処理だけ管理用接続を使い、リポジトリ操作は `assay_app` に接続し直す。本番と同じ `ops/app_privileges.sql` を適用し、42501 と所有者向けの 0A000 を区別して検証する

### 名前

- **「ユナメイト」を使わない** — 商標を省略・改変した名称の使用がガイドラインで認められていない
- **`unite` / `unity` を含む名前を使わない** — 上と同じ基準に抵触する。`unityhub` は Unity Technologies の実在プロダクト名でもある
